# Being Desktop：交互架构复审

2026-09-27。交付范围是整体交互审查和下一轮设计依据，本轮没有修改产品代码。**这不是上一版界面的验收记录。**

**后续研究：**用户要求进一步比较多窗口、标签、浮动对话、自由组合和 Being 自主安排。本稿将固定左中右视为唯一方案的推荐已撤回；它保留为默认布局候选。最新组织研究见 [场景、标签、窗口与共同操作](UIUX-SCENE-PRESENTATION-2026-09-27.md)。以下问题证据、功能覆盖和状态边界继续有效，具体功能位置需按新方案重新安排。

## 1. 范围、证据与已确认决定

面向每天与同一个 Being 相处、讨论和做事的人类伙伴。审查范围包括 Desktop 的导航、场景、对话、共同阅读、小镇、工具、设置和系统流程；按上一份全量图谱的 A01–N07 逐项安排归属。重点是交互架构，不是全客户端像素、读屏或服务端验收。

本轮重新读取了最新 spec v2.2、参考档案、重设计总纲、导航实施记录、全量功能图谱，以及当前导航、设置、Town 阅读恢复、回复、安装和共同上下文代码。Being 的定位回看了本地 `Workspace/being/architecture/about-heart.md`、`chronicle/2026-08-13-定位校准-being-不是-通用-agent.md`；只使用持续身份、关系、记忆和自主行动的概念，未采信旧资料中的实时数量、版本或能力清单。

证据等级：

- **代码确认**：mine 的当前未提交源码；不是已安装客户端的运行结论。
- **预览复现**：`http://127.0.0.1:4186/collaboration.html`，真实共享组件、模拟数据。复现了设置往返导致右侧私信消失。Portal 内容本身在该 demo 中不完整，不能据此判断正式 Portal 面板缺内容。
- **参考实看**：Behance / Dribbble 作品的可见图片和作者说明；Linear、Slack、Notion、Dia 的官方说明。概念稿不作为已验证交互的证明。
- **未验证**：安装中的 Electron、真实 Being / Town 写操作、macOS 原生网页叠层、读屏、真实跨端状态。本轮不重复先前被系统拒绝的原生捕捉。

证据目录：[观察记录与来源](ux-audit-interaction-architecture-2026-09-27-evidence/observations.md)。

### 用户已确认

1. Being 是持续的 person Agent；新建场景不产生新 Being，切换模型也不等于换一个 Being。
2. 左中右结构，中间主对话，右侧可以看原文并回复，中间继续讨论。
3. **本轮确认：切换场景时，恢复该场景自己的阅读现场。**不再沿用“右侧在所有场景间独立不动”的实现规则。
4. 功能不能因极简被遗漏；先理清逻辑，再进行 UI 设计。

下文的入口位置、设置分类、内容选择器是**本次推荐稿**，尚未获得整体方案认可。第 3 条已确认决定优先于旧 `UIUX-NAVIGATION-REFACTOR-2026-09-27.md` 中“切换聊天场景不关闭右侧”的规则。旧文档保留为实现历史，不再据此决定新行为。

## 2. 结论

上轮做的是功能分组，没有形成一致的空间模型。左侧的场景和“交流 / 阅读 / 工具库”长得像同一级导航，却分别控制中间和右边；右边又重建分类、栏目、列表筛选和详情返回。设置总页把用户带到多个不同的容器，返回还会改写阅读位置。它们不是靠减小图标、加圆角就能解决的问题。

新的组织单位应当是**人与同一个 Being 的一个场景：对话、正在看的内容、未完成的草稿和这件事的行动结果**。小镇是访问外部社会与知识的入口，不是另一个 Being，也不是主对话的竞争首页。浏览内容和交给 Being 作为上下文，是两个不同动作。设置负责配置其所属对象，不参与阅读历史。人和 Being 应使用相同的对象、动作和结果记录，但各自浏览不抢对方的位置。

### 优先收益

| 优先级 | 要解决的事 | 用户能直接感到的变化 |
|---|---|---|
| 1 | 场景同时恢复对话和右侧现场 | 从工作切到日常，再回来，原信、位置、草稿都对得上 |
| 2 | 设置使用独立路由与固定容器 | 改完模型或修好连接，仍回到刚才那封信 |
| 3 | 左侧只承担场景导航，内容入口归右侧 | 每次点击能预期哪个区域会变 |
| 4 | 移除“交流 / 阅读”中转页面层 | 直接到私信、卷轴、工具库，减少标题和标签堆叠 |
| 5 | 讨论、拟稿、发送构成连续流程 | 写作要求说一次，最终发送的正文和身份明确 |

这些包含结构改造，不能包装成几个低成本样式修补。小范围可独立修正的是标签、入口一致性和设置恢复；实施前仍应先按本稿的状态契约设计。

## 4. 当前问题与证据

### NAV-01 · 同一左栏有两套当前位置

- **维度 / 类型 / 严重度：**信息架构；缺陷；High。
- **证据：**`app/components/chat-scene.tsx:224` 的场景选择，与 `workspace-navigation.tsx:7` 的栏目导航同处侧栏；后者按 `groupForView(app.view)` 标记当前项，前者按 `scene_id` 标记。预览中“今天，接着聊”和“交流”同时选中。
- **可信度：**Observed（代码 + 共享组件预览）。
- **后果：**用户不能仅凭选中状态判断是在换整件事、换对话，还是只换右边。
- **建议：**左栏只选场景；内容选择器放到它控制的右侧。选场景时恢复整个场景的对话与阅读状态。
- **工作量：**L，涉及状态和外壳，不是重新排按钮。

### CTX-01 · 阅读恢复没有归属到聊天场景

- **维度 / 类型 / 严重度：**状态与连续性；与本轮已确认需求冲突；High。
- **证据：**`town/models/town.ts:941` 的 `readingLocations` 仅按 `view` 保存；`app/models/app.ts:30` 的栏目最近位置也是全局表，没有 `scene_id` 分区。
- **可信度：**Observed（代码）；跨真实客户端恢复未验证。
- **后果：**从工作切到日常后仍面对工作私信；回到场景时也不能可靠还原当时的整套现场。
- **建议：**阅读位置与展示偏好属于场景；源内容、Town 身份、已安装工具仍是全局对象，不复制成每场景一份。
- **工作量：**L。

### NAV-02 · 分类成为了额外页面层，还带来不稳定落点

- **维度 / 类型 / 严重度：**导航与命名；缺陷；Medium。
- **证据：**`app/models/navigation.ts:2` 创建“交流 / 阅读”；`openPlaceGroup` 回到最后访问的子栏目；`components/navigation.tsx:35` 再铺栏目条，Town 自己还有本页 tab 与筛选。预览私信顶部依次出现“交流”、五个栏目、“全部 / 收件箱 / 已发送”和搜索筛选。
- **可信度：**Observed（代码 + 预览）。
- **后果：**点“交流”有时到私信，有时到公告；用户为了看原文要穿过多层同等强度的导航。“阅读”也不足以代表经验种子的关系和内化记录。
- **建议：**分类仅用于打开菜单中的分组标题；选择“私信”就到私信，面板标题也叫私信。恢复位置在该明确目的地内部发生。
- **工作量：**M。

### NAV-03 · 设置返回改变了阅读现场

- **维度 / 类型 / 严重度：**中断与恢复；缺陷；High。
- **证据：**`app/models/app.ts:515` 的 `returnToClientSettings` 将非 chat 视图导航到 chat；`openModelSettings` 和 `chatAction` 也调用 `navigate("chat")`。预览复现：私信 → 设置 → Portal 运行状态 → 回退 → 关闭设置，右侧私信消失。
- **可信度：**Observed（代码 + 共享组件预览）；不是原生 Electron 实测。
- **后果：**用户只是修配置，却被带离正处理的事情。
- **建议：**设置独立保存调用来源，关闭恢复原场景、右侧对象、焦点和草稿。设置内部路由不得调用阅读导航来表达返回。
- **工作量：**M–L。

### SET-01 · 入口重复之外，更根本的是配置归属混合

- **维度 / 类型 / 严重度：**信息架构；缺陷；Medium。
- **证据：**Being 名称按钮的标签是“设置与连接”，其中有“设置”；底部再有“设置与连接”。设置的“连接与 Being”下放 Being 连接、本机配置、Town 身份、模型、Portal 运行状态和打开文件夹。`settings.tsx:10` 每次打开还重置到连接分类。各子项打开不同容器。
- **可信度：**Observed（代码 + 设置首页预览）。
- **后果：**名字入口不像一个人，设置首页像跳转目录；用户不知道开关影响 Being、客户端还是本机服务。
- **建议：**一个应用内设置入口；分类按影响对象；上下文中的“修复连接”是到同一设置页的快捷路径。系统菜单和快捷键可以保留，不机械删除有用的别名。
- **工作量：**L。

### FLOW-01 · 讨论与拟写回复被拆成两处意图输入

- **维度 / 类型 / 严重度：**输入与核心流程；改进机会；Medium。
- **证据：**`town/components/composer.tsx` 除正文外还有“给 Being 的要求”；中间主对话也接受相同意图。`town/models/town.ts:1409` 构造的是“拟一段回复，直接发送”的请求，关闭编辑器。当前标签已经明确代发，不能再说它完全没有告知。
- **可信度：**Observed（代码）；未进行真实代发。
- **后果：**用户在中间商量完，还可能到右边重复填要求；讨论结果缺少明确地放入回复正文的衔接。
- **建议：**写作要求主要在中间说；右边只编辑最终正文。给出“放入回复草稿”动作，已有正文时可选择替换或另存版本。直接委托发送保留为明确动作，不能由“讨论 / 拟稿”默认触发。
- **工作量：**L，需要结果与草稿的真实协议，不能只造按钮。

### FLOW-02 · 安装等待占住整个工作区

- **维度 / 类型 / 严重度：**阻塞与反馈；改进机会；Medium。
- **证据：**`town/components/kit-install.tsx:10` 使用 `Dialog busy={installBusy}`，安装时关闭禁用。`desktop/main/kits/install.ts:152` 安装依赖、写配置和移动目录；没有取消操作接口。
- **可信度：**Observed（代码）；真实等待时间本轮未测。
- **后果：**本可在安装期间继续讨论，却被模态层挡住。
- **建议：**审阅配置时用短表单；提交后转为可收起的事务进度。收起继续执行，取消只在真实支持时出现。完成结果留在来源场景，不抢当前场景。
- **工作量：**L；仅去掉遮罩不足以解决事务生命周期。

### NAV-04 · 多套返回记录无法表达连续跨对象浏览

- **维度 / 类型 / 严重度：**导航与恢复；缺陷；Medium。
- **证据：**`town/models/town.ts:605` 等处使用一组 `returnView / forwardView`，安装另有 `kitReturn`，引用另有 `selectionLocations`；`PlaceHeading` 在安装后可同时出现“返回安装来源”和“返回…列表”。
- **可信度：**Observed（代码）；长链返回的全部结果仍需实现后验证。
- **后果：**Kit → 经验墙 → 种子 → 网页等连续路径，靠一个上一页字符串和特例不能统一解释；关闭、回列表、回来源易混。
- **建议：**每场景的内容区维护可恢复的访问栈；后退只回上一访问，面包屑是明确上层，关闭只收起。安装来源是带对象 ID 的链接，不是另造一组浏览器按钮。
- **工作量：**L。

### STATE-01 · “看到回复”的判断仍依赖旧全屏页面模型

- **维度 / 类型 / 严重度：**反馈；潜在缺陷；Medium。
- **证据：**`app/models/app.ts:64` 只有 `view === "chat"` 才把当前场景完成的回复加入已读集合；并排时中间仍可见，但 `view` 是 mail 等。
- **可信度：**Observed（代码）；实际误报未在真实流式事件中复现，用户影响为 Inferred。
- **后果：**可能出现人正在看的对话仍提示新结果。另一方向也不能仅凭面板显示就宣称人已读。
- **建议：**拆开“加载成功、可见、滚到该回复、用户清除提示”；场景提示由明确可见性规则维护，与右侧路由无关。
- **工作量：**M。

## 5. 重建对象关系

| 层级 | 对象 | 拥有什么 | 不随场景切换的事 |
|---|---|---|---|
| 持续关系 | 同一个 Being | 身份、已有长期记忆与自主活动；在 Desktop 中显示真实可取得信息 | 不因切场景改姓名、模型配置或 SBS |
| 当前事情 | 场景 | 对话、主草稿、引用、右侧阅读访问记录、关联行动结果 | 不复制 Town 的私信、工具安装、凭据 |
| 社会与材料 | 私信 / 围炉 / 卷轴 / 书架 / 花园 / Kit / 网页 | 稳定来源、对象 ID、版本、可见范围、可执行动作 | 相同对象在不同场景仍指向同一份源内容 |
| 一次行动 | 发送、委托、安装、配对、重启 | 发起场景、目标、执行身份、阶段、结果与返回来源 | 导航离开不能改变已提交动作的目标 |
| 应用与设备 | 客户端、Portal、Town 凭据 | 全局偏好、连接、本机能力、诊断 | 通过独立设置层管理，不伪装成聊天场景 |

场景是组织共同经历的容器，不承诺 Heart 因此产生完全隔离的内部记忆。场景中的阅读恢复也不意味着内容已发送给 Being。

### 人和 Being 如何共同操作

1. **同一个对象。**人点的是那封信；Being 收到的也是带稳定来源与目标的那封信，不是任意时刻的“当前页面”。
2. **同一套动作含义。**查看、引用、拟稿、发送、安装分别有明确结果。UI 与未来 Agent 接口复用语义动作，避免让 Being 靠坐标猜按钮。
3. **各自的注意力。**Being 可以在后台查资料；结果先回发起场景。除非人明确要求打开，不自动切换人的当前页。
4. **可见的共同上下文。**“一起看”先放入当前草稿，显示范围、来源和截断；发送后才记录随哪条消息发出。打开网页、加载列表、引用已入草稿，都不能标成 Being 已读。
5. **明确的行动边界。**常规导航无需确认；明确委托可以执行。发送、删除、换身份等按实际影响说明目标，复用已有授权，不把每步都做成审批。
6. **状态可追溯。**已接受请求、执行中、执行结束、Being 已回复、发送已确认是不同事实。遇到未知结果先核对，不自动重复代发。

现有能力是显式引用、scene_id / scene_meta、部分本地观察与动作记录。完整 UI 读写协议和 Being 侧回执仍是待接线能力，不能在原型中伪装成已经同步的“共同视野”。

## 6. 三种组织方式与推荐

| 方案 | 具体结构 | 收益 | 代价 / 判断 |
|---|---|---|---|
| **A · 场景侧栏 + 右侧内容入口，推荐** | 左侧只选场景；右侧从“打开…”选择私信、卷轴、工具或网页 | 点击影响范围与空间一致；场景恢复形成完整连续性；无新主栏 | 内容入口需要第二次点击选目的地；通过当前内容标题、最近访问和对象直达弥补 |
| B · 左侧切换“场景 / 小镇”目录 | 顶部切换器只改变左栏目录；中间仍是原场景，右侧显示内容 | 小镇功能更多时目录可充分展开 | 管理内容时场景列表暂时不可见；要同时理解“目录模式”和“当前场景”，增加一个状态 |
| C · 全局应用导航切到小镇 / 工具 / 对话 | 主区域随应用栏目整体切换，再按需开 Being 对话 | 适合把多个独立应用装进一个客户端 | 与已确认的中间持续对话冲突，不推荐作为默认；大范围阅读只能是用户主动的临时放大 |

选择 A 的依据是 Being 的定位和已确认的场景恢复，不是某个软件也这么画。

### A 的可见布局

─────────────────────────────────────────────────────────────────────────
美阳阳                           工作讨论  ⓘ  查找                  打开…
新建场景
                                 对话正文                          私信 › Alice
场景列表                                                           原信 / 回复正文
  工作讨论  ●                    相关行动的简短进度
  读到一半的书

这只是层级图，不是字体、间距、色彩或最终组件稿。沿用现有场景排序；现有“固定”指固定整个侧栏，不把它误写成已支持收藏场景，也不新增任务项目体系。

### 左侧

- 顶部 Being 姓名打开“关于这个 Being”的真实资料与状态；不再兼任退出、检查更新、文件夹等杂项菜单。
- 场景列表是唯一主选中项。日常使用“新建场景”；“绑定已有场景、排序、多选、复制 ID、从本机移除”保留在可发现的场景操作中。
- 场景信息仍在中间标题旁常驻。右键是加速路径，不是唯一入口。
- 底部一个“设置”；系统菜单、快捷键到同一个目的地。浏览器不放在设置旁边。
- 不默认增加“任务”“记忆”“活动中心”三套新列表。场景正在做什么、哪里有新结果由场景行与相应对话呈现。

### 中间

- 标题回答“我们现在在哪个场景”；查找、历史显示范围属于本场景视图操作。
- “显示全部场景记录”移到对话的显示选项，文案不再叫“全部上下文”。开启后仍明确发送到哪个场景，不能暗示改变 Being 的记忆或模型上下文。
- 一个自然语言意图输入。正文、附件和引用属于当前场景；工具过程默认简要，详情可展开。
- 窄窗口优先临时收起左栏，保留中间和右侧的有效宽度；再窄时显式切换“对话 / 当前内容”，不在三栏里压出第四、第五列。

### 右侧

- 右上固定 **“打开…”** 命令。右栏收起时也能从窗口右上找到；它是打开内容的动作，不呈现为另一项左侧选中导航。无 tooltip 也能读到文字。
- 菜单按小镇、阅读与经验、工具、网页分组。分组标题不点击、不另开空页面。直接入口保留原名：小镇概览、私信、围炉、篝火、通讯录、公告、卷轴、书架、花园、工具库、打开网页；工具库内再分发现 / 本机。
- 本页标题如“私信”可直接切换目的地，与“打开…”调用同一个内容选择器。右侧已打开时不再同时显示第二排全功能按钮。
- “私信”明确回私信，不会因之前看过公告而改变落点；在私信内部恢复筛选、对象与滚动。
- 内容只有位置栏、本页必要工具和正文。详情中用一条面包屑回列表；筛选只属于列表，不压在长文上方。读原文与回复可上下共存。
- 默认只显示一份内容；历史负责返回。不是一打开每种栏目就新增一个永久标签。只有用户明确需要保留多个对象时，才引入可关闭的保留项；此项不作为首轮必做。
- 放大是展示变化；恢复并排回同一对象。关闭只是收起内容，不等于删除对象、丢草稿或终止任务。
- 小镇概览保留为可浏览的社会空间目录。它可以有自己的表达，但不能取代默认对话、也不能只缩成一个无文字地图图标。

## 7. 设置：按作用对象归位

**固定的一层设置容器，固定的分类列表，分类直接展示真实设置。**不再先有一个“链接集合”总页，然后跳进 Town 弹窗、聊天 iframe 和右侧 Portal。布局上可临时覆盖工作区；关闭后完整返回。保存、修复与失败停留在同一容器。

| 分类 | 内容 | 边界 |
|---|---|---|
| 客户端 | 外观、正文字号、通知、客户端登录启动 | 影响 Desktop 的呈现与系统行为，不影响 Being 是否自主醒来 |
| Being | 当前连接、模型与实际支持的生成参数、自主醒来 SBS | 这些影响当前 Being 或其连接；模型更换不伪装成人格切换 |
| 本机能力 | Portal 状态、工作目录、命令 / Kits / subagent 开关、subagent 模型、后台与启动策略、日志 | 区分当前服务状态与长期启动配置；“停止”实际影响以底层能力为准 |
| 小镇身份 | 当前配对身份、自动 / 手动配对、已有凭据、断开 | 显示真实 Town 身份；与当前对话 Being 不一致时在实际发送位置说明 |
| 关于与诊断 | 版本、更新、连接诊断、导出、隐私与帮助、原版 Loom / 小镇说明链接 | 更新进度不等于取消按钮；支持链接可以打开内容，但设置来源保留 |

- Being 资料中的“自主醒来”“模型”状态可打开对应设置项，**不维护第二套独立开关和表单**。若后续需要常用快捷开关，也必须操作同一配置并同步实际状态，不先默认堆上两套。
- 本机工具的安装、浏览、导入、删除在工具库 / 本机页，是做事，不是偏好设置。设置里的 Kits 总开关只管理本机能力是否启用；两者有明确互达入口。
- 某个 Kit 的配置属于该 Kit 详情。不要新建一个内容相同的“插件设置中心”。当前没有完整凭据编辑器的能力，要单独实现，不能画完就称为具备。
- 连接失败旁的“修复连接”、私信旁的“连接小镇”是**同一目的地的带来源快捷入口**，不是重复设置。只保留一个事实来源、一个编辑状态、一条保存逻辑。
- 分类切换保留填写内容；立即生效项不显示虚假的保存按钮。需要提交的连接、模型或凭据表单显示待应用状态；离开未保存表单才问保存 / 放弃，不对普通浏览打断确认。
- 去设置前保存 `returnTo`；如果配置改变了身份，不能恢复旧身份的私有内容，应回到仍有效的公开来源或明确的重新授权状态。
- SBS、自启、Portal 存活、Relay 连接和工具就绪各有真实来源，不能合成一个“在线”点，也不能因为某个开关开着就显示 Being 正在思考。

## 8. 完整往返流程

### 8.1 看私信，商量，再回复

1. 在“工作讨论”场景通过“打开… → 私信”找到 Alice。原场景不变。
2. 打开原信；点“一起看”把选定原文放入中间草稿。原文仍在右侧，来源和范围可查看；尚未发送。
3. 在中间说“先帮我想想怎么回”。Being 在同一场景讨论。右边可以同时写最终正文。
4. 采用某段建议时执行“放入回复草稿”；已有正文先选择保留 / 替换，不把整段思考过程当信件正文。
5. 右侧明确显示发件身份、收件人和回复对象。人点击发送；确认结果回到原信，不跳到列表顶部。
6. 若明确选择“委托 Being 拟写并发送”，动作保留原信 ID、收件人和发起场景。待发送 / 已确认 / 未知结果就地可查；这条路径不与普通讨论混用。

“放入回复草稿”与结构化代发回执是需要接线的新能力。过渡阶段可人工复制，不能用无反馈按钮冒充闭环。

### 8.2 讨论一半切场景，再回来

工作场景：Alice 原信 + 回复草稿 → 切“日常聊天” → 恢复日常自己的内容或纯对话 → 回工作 → Alice 原信、滚动、引用和草稿恢复。

阅读位置按场景保存；Town 回复草稿按发送身份 + 目标 + 原消息归属，在两个场景看到同一封信时仍引用同一份草稿，不能克隆出两份可能重复发送的正文。若另一处已发出，回到旧场景显示已发送结果，不复活旧草稿。

### 8.3 从工具库到安装、配置、使用

工具库 → Kit 详情 → 安装审阅 → 执行中可收起 → 完成留在原详情。下一步按事实提供“继续浏览”“查看本机”“处理配置”；不强行跳页。

进入本机详情时保留来源对象；后退回原 Kit。需要修 Portal 或授权时进入同一设置 / 配置容器，保存后回该 Kit。通过真实检查才显示相应就绪状态。安装文件成功、Portal 发现、工具启动、第三方服务授权分别核实；当前安装源码只返回文件安装和按需启动说明，README 中更强的工具检查表述不能替代代码证据。

若安装由工作场景发起、完成时人在日常场景：结果归工作，不拉走人；给原场景低干扰提示。正在等待的安装在 Scene 删除、窗口隐藏和退出时也要有可解释归属，不能依附一个临时详情组件。

### 8.4 设置、配对与故障修复

看私信 → 连接过期 → 原位“重新连接小镇” → 设置中的小镇身份页 → 成功 → 回到原私信并重试读取。**不自动发送之前那封未发送的信。**

自动配对已发出请求后允许收起；取消等待不谎称远端请求已撤回。若换成另一个 Town 身份，旧私有缓存与草稿按身份隔离，不能自动带到新身份发送。改模型后仍回原场景；改变 Being endpoint 才是身份边界，需要正确隔离旧现场。

### 8.5 长链阅读与网页

Kit → 经验墙 → 种子 → 相关卷轴 → 网页：右侧一路接续，后退逐项还原来源、筛选和滚动。进入网页后有网页自己的前进 / 后退，外层“返回卷轴”是来源返回，不能用两组同名箭头让人猜。

当前浏览器只有一个 WebContentsView。要支持各场景完整网页现场，必须选择并实现页面实例管理；在这之前，最多保证可恢复地址与能可靠取得的位置，不能承诺恢复网页表单、任意 SPA 状态和原生浏览历史。这个限制必须在原型验证与实现计划里明写。

### 8.6 主动活动、后台结果与通知

自主醒来继续是 Being 层能力；场景切换不改变 SBS。活动只按已有真实事件呈现。后台任务保留原场景，结果抵达时标记该场景；人明确点开再切换。不假设一次自主活动一定归属当前打开的场景。

Town 通知先定位稳定目标，不能静默把私信正文塞入主输入。若通知目标已属于某场景，回那个现场；没有关联时在当前场景打开内容，并清楚标明来源。需要为“另起场景讨论”提供显式动作，不自动批量制造场景。现有通知只能到栏目或围炉时，必须维持这个真实精度。

| N07 | Dialog、popover、编辑菜单 | 同一焦点和层叠规则；native 网页也服从遮挡，Esc 只关闭最上层 |

**未当成已有功能：**搁置 / 共同物件持久库、完整记忆管理、全局全文搜索、完整 Being UI 操作回执、任意网页内容一起看、完整网页会话恢复。保留在后续能力表，不用空页面提前占主导航。

## 10. 状态、边界与返回契约

| 状态 | 保存归属 | 切场景 / 收起 / 重启 |
|---|---|---|
| 主草稿、引用、附件记录 | Being endpoint + scene_id | 切场景保留；需补重启持久化。附件不能恢复时逐项提示，不清空整段文字 |
| 内容目的地、对象、列表筛选、页码、滚动、是否收起 | Being endpoint + scene_id + 授权身份引用 | 随场景恢复；授权失效不读旧私有正文；重新加载不自动跳顶 |
| Town 回复正文 | Town 身份 + 渠道 + 收件目标 + 回复消息 | 场景引用同一份草稿；已发送不能被旧现场复活；重启保存需实现 |
| 待发送 / 执行中动作 | 独立 action_id + 发起场景 + 固定目标 | 切页不改目标，不重发；结果归原场景；未知结果提供核对 |
| Settings 页面 / 未提交值 / 调用来源 | 独立 settings route + returnTo | 关闭不改阅读；改变身份时验证 returnTo 是否仍可访问 |
| 模型、SBS、Portal 策略、Town 凭据 | 各自真实服务 / 本机配置 | 不随普通场景恢复而回滚全局配置 |
| 网页实例 | 当前实现为一个原生视图 | 多场景恢复不能仅保存 URL 就宣称完整现场；先确定实例生命周期 |

统一动作词：

- **切换场景**：恢复整套场景现场，不改变 Being。
- **打开内容**：在当前场景右侧访问一个明确目标。
- **后退**：撤回一次内容访问，恢复离开时的页面状态。
- **回列表**：去该对象所属列表，不伪装为历史后退。
- **收起**：暂时隐藏，草稿和已提交动作仍在。
- **一起看**：把显式选定内容加入对话草稿；不是自动上传全页。
- **拟稿 / 讨论**：产生可审阅内容；不暗含发布。
- **发送 / 委托发送**：对明确的身份和目标提交动作；反馈实际确认阶段。
- **打开设置**：进入独立配置层；关闭回调用现场。

状态设计至少覆盖以下组合；下表是下一轮必须设计并验证的合同，不是当前全部通过：

| 区域 | 初次 / 空 | 载入 / 更新 | 失败 / 离线 / 授权 | 中断 / 返回 |
|---|---|---|---|---|
| 场景与对话 | 已连接但无场景、未连接区分 | 切换不闪整页，回复不强拉阅读 | 保留本地内容和草稿，发送待确认不盲重试 | 恢复原草稿与阅读；更新前验证落盘 |
| Town 列表 / 详情 | 无内容与筛选无结果不同 | 刷新旧内容时保留可读正文 | 公开内容可读；私有内容进入带来源配对；部分加载单独提示 | 原筛选、对象、位置；对象不存在时回有效列表并说明 |
| 回复 | 有明确目标才能撰写 | 提交期间冻结本次内容与目标 | 已发送、部分成功、结果未知各有下一步 | 取消编辑保留；取消发送只能在能力允许时承诺 |
| 工具安装 | 未安装、状态未知分开 | 审阅 / 下载依赖 / 文件落盘各有阶段 | 缺依赖、配置变化、凭据失败就地恢复 | 收起继续；重新打开同一事务，不再开第二次安装 |
| 设置 | 未配置与不可读取分开 | 已保存、待应用、保存中明确 | 字段失败保留非敏感输入；身份变化作废旧返回目标 | 回原分类 / 原工作；焦点回发起控件 |
| 网页 | 空白地址可输入 | 网页加载与 Portal 状态无关 | 失败保留地址，授权交给真实网页机制 | 保留实例或如实说明重新载入；没有假“恢复全部” |

## 11. 与旧 spec / 文档的取长补短

| 旧要求 / 实现 | 保留或修正 | 理由 |
|---|---|---|
| 安静、真实状态、中性色、文字主导 | 保留 | 支持长期使用；不是把必要入口淡到看不清 |
| 每屏只有一个主角 | 解释为“一件事有明确主次” | 私信协作需要对话和原文同时有效；不能按字面只留一个可操作区域 |
| 中间圆角阅读面 | 保留为下一步视觉变量 | 一个外壳表达层级；内部正文不再套层层卡片 |
| 中间最大阅读宽度 680、正文 17 | 作为目标并按桌面空间验证 | 两个内容区并排时用有效行长验证；375px 是另一个响应式状态，不强塞桌面三栏 |
| 进门摘录 + 未读消息 | 收紧为可选冷启动恢复 | 已有现场优先；服务没有真实摘要时不虚构；暖返回绝不插入欢迎仪式 |
| 左侧交流 / 阅读 / 工具库 | 撤回这一组织建议 | 控制区域混杂、分类重复、落点不稳定 |
| 各栏目全局记忆最近位置 | 改为每场景现场 | 本轮用户已确认；源对象和身份继续独立 |
| 设置总页逐个跳到不同容器 | 撤回 | 改为同一配置层与同一返回合同 |
| “物件 / 搁置 / 记忆”入口 | 留作明确后续能力 | 不能用 demo 的虚构存储覆盖真实 Desktop 的能力边界 |
| 参考档案中的装饰性光点 / 动效来源 | 降为视觉探索 | 交互依据以状态接口和真实任务为先；作品营销描述不是运行证明 |

## 12. 实施顺序与验证重点

1. **先确定本稿的入口组织。**已确定场景恢复；推荐 A 的具体入口仍待用户审阅。下一步制作低保真、可点的流程图，先展示场景切换、私信讨论、设置往返和安装返回，不先包装新皮肤。
2. **重构状态归属。**将阅读按场景索引；资源与草稿规范化；分离 settings route、内容访问栈和长操作状态。优先保护已存在的草稿与场景数据，迁移不能重置用户现场。
3. **落统一设置。**保留全部字段与原有平台差异；合并的是入口、作用范围和路由，不删功能。确认副作用与保存时机，再调整表单。
4. **接续人 / Being 操作。**先做引用与结果的准确来源，再做建议稿到正文、代发回执；不靠纯文本猜测“是否已发出”。
5. **最后落视觉与细节。**按同一位置栏、工具栏、正文、局部反馈结构覆盖各类面板，逐个展示真实运行效果。圆角、字号和留白围绕实际长文与操作量调，不用空 demo 验收。

优先验证的真实任务：

- 工作场景有主草稿 + 私信回复草稿 → 切日常 → 返回，内容和发送目标都正确。
- 看信 → 任一设置类别 / 子页 → 保存或取消 → 仍是原信、原位置。
- Kit → 经验墙 → 种子 → 网页 → 连续后退，逐层恢复；无来源则不给无效返回。
- 安装中切场景，完成不抢焦点；重新查看仍是同一事务。
- 两个场景打开同一回复，发送一次后另一处不复活旧草稿。
- Town 换身份、Being 换连接、断网恢复，旧私有数据与旧目标不串用。
- 停止生成、取消排队、收起网页、退出客户端分别呈现真实结果。
- 键盘走完打开、引用、讨论、回复、设置返回；焦点与 Esc 范围一致。

**保留的好基础：**同一个主聊天 iframe 持续存在、显式引用、场景 ID、来源记录、正文与代发要求已经分字段、安装来源保存、浏览器不再长出第四主栏。这些是可继续使用的基础，不应因本轮批评全部推倒重写。

**仍需决定 / 验证：**推荐 A 与 B 的目录方式；原生网页在多场景间的实例成本；消息与动作稳定回执；重启草稿恢复；低保真阶段的可发现性。没有用“最前沿”替代这些具体问题，也不以测试通过证明设计已经被认可。
