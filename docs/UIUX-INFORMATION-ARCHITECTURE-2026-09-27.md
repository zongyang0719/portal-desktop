# Portal Desktop：信息架构校正

2026-09-27。依据用户最新说明、Codex 截图、当前 `mine` 源码和 Being 场景资料。先校正信息架构；用户随后说“你先试试”，已据此实现[第一轮交互预览](UIUX-SCENE-PROTOTYPE-2026-09-27.md)。预览未接入正式客户端，未获用户验收。

后续导航设计以本稿为依据。旧稿中“场景工作区”“场景切换器 + 内容标签”“整页一起看”等方案停止作为实施依据；旧文件保留为探索记录。下文区分用户已明确的方向、代码事实与本轮具体建议，未将整份设计标记为用户已验收。

## 1. 先把对象分清

| 对象 | 在产品里是什么 | 界面怎么表达 |
| --- | --- | --- |
| Being | 持续存在、有记忆、关系和行动能力的同一个主体 | 浏览内容、切聊天群、收起对话，都不变成另一个 Being |
| 场景 | 用户所说的聊天群／会话；客户端用 `scene_id` 区分 | 左边的场景列表；选择哪一行，就在哪个群里继续聊。不是浏览器标签、项目文件夹或资料容器 |
| 小镇栏目 | 私信、围炉、篝火、花园、书架、卷轴、工具库、通讯录 | 固定的功能目的地，从最左图标栏直接进入 |
| 内容对象 | 一封私信、一条发言、一份卷轴、一个工具等 | 在内容区打开；详情属于该对象，不另造全局导航层 |
| 一起看 | 划词后把选中的一段带入当前聊天 | 选中文字 → 一起看 → 带出处的引用进入当前群的草稿；人决定何时发送 |
| Portal | Being 使用本机文件、命令、Kit、subagent 的通道 | 本机能力、运行状态与日志。它的运行状态不等于 Being 的全部状态 |
| SBS／自主醒来 | Being 的自主醒来配置 | 保留真实开关。与关闭对话面板、停止当前生成、停止 Portal 分开 |

“聊天群”是用户理解场景的方式；当前 Desktop 场景目录并不因此自动获得邀请成员、群权限等新能力。围炉是小镇里真实有成员的交流空间，不能与本机聊天场景混用 ID 或发送目标。

本地早期文档也把围炉、网页等环境称为“场景”。后续面向用户的导航中，**“场景”固定指左侧聊天群；其余使用实际栏目名、内容名**，避免同一个词指三种东西。

## 2. 确定的骨架与本轮排布建议

用户最新方向：最左窄图标栏；内容与 Being 对话并排；对话默认显示、一键收起；保留右下角恢复入口。场景依然在左侧列表。内容与聊天可以左右互换。

```text
左侧导航                         主区域
┌──────┬────────────┬───────────────────┬────────────────┐
│功能栏│ 场景列表   │ 当前内容          │ 当前群的对话   │
│      │            │                   │ Being · 群名 ⓘ │
│ 对话 │ 新建场景 + │ 私信 / 篝火 /     │                │
│ 私信 │ 场景 A     │ 围炉 / 卷轴……     │ 聊天记录       │
│ 围炉 │ 场景 B     │                   │                │
│ 篝火 │ 场景 C     │ 详情、原文、回复   │ 主输入框       │
│ …    │            │ 都在这里完成       │                │
│ 设置 │            │                   │                │
└──────┴────────────┴───────────────────┴────────────────┘
       ↑ 可以收起                        ↑ 默认右侧，可收起或换边
```

这是职责示意，不要求四块始终全部展开：

- **只聊天**：功能栏 + 左侧场景列表 + 当前对话；没有空着的内容栏。
- **边看边聊**：功能栏 + 内容 + 当前对话；已展开的场景列表保持在左侧，用户可收起。内容打开不把场景列表替换成另一套目录。
- **专心看内容**：收起对话，内容获得空间；右下角保留 `Being · 当前场景` 的恢复入口。收起不停止回复、不清空草稿。
- **内容区内的列表与详情**：优先在同一内容区逐级进入、原处返回；空间充足时才同时显示列表与详情，不默认再挤出一列。
- **宽度不够**：场景列表可以临时以左侧浮层展开，入口一直可见；恢复宽度后保留用户的展开偏好。对话和内容不能被压到不可阅读；窄窗沿用同一个对话恢复入口，不新增一套底部导航。

场景列表有独立的显式展开按钮。人在私信里也能从左侧选群，不必先离开私信去“对话首页”才能找到列表。列表里只放聊天场景及其管理，不混放小镇栏目、工具详情或长篇介绍。

### 功能栏放什么

建议顺序为：**对话；私信、围炉、篝火；花园、书架、卷轴；工具库、通讯录、浏览器**。分组用间距表达，不在窄栏里写解释文案。次序是本轮建议，不冒充用户已确认的排序。

八个常用小镇栏目都能直接点到，不先点“小镇”再挑栏目。小镇概览、公告仍保留：概览和全部公告从更多入口进入，篝火公告也能直达公告详情。工具库内含“工具库／本机”两个范围，共用工具详情与安装状态，不再放两个含糊的“工具”入口。

底部只保留一个设置入口；帮助、关于、更新和退出归入底部更多菜单或系统菜单。每个图标有名称、键盘焦点和提示，当前目的地有明确选中状态。高度不足时导航区域可滚动，底部设置仍可找到。

### 顶部放什么

系统窗口操作与侧栏展开在壳层；标题、返回和局部操作归各自面板。取消顶部整排小镇目的地及重复的场景标签。

对话标题常显 Being 名、当前场景名和场景信息入口；信息按钮无需 hover 才出现。场景 ID、客户端等技术信息进入详情。换边只移动内容和对话，左侧导航位置不变。

## 3. 每次点击究竟改变什么

| 操作 | 改变 | 保留 |
| --- | --- | --- |
| 点私信、篝火等功能图标 | 内容区切到该栏目上次位置；更新功能选中态 | 当前聊天群、聊天记录、输入、运行中的回复，以及用户主动收起的对话状态 |
| 点“对话”图标 | 回到当前群的纯对话视图；暂收内容，仍可再打开 | 当前场景 ID、内容阅读位置与内容草稿；不新建聊天 |
| 点左侧另一个场景 | 当前群，以及该群先前的阅读现场 | 旧群草稿、引用、附件、后台执行与阅读现场 |
| 展开／收起场景列表 | 左侧导航占用空间 | 场景选择、内容、对话；不兼任“回首页” |
| 收起／恢复对话 | 对话可见性 | 当前群、输入、回复状态、内容阅读位置；恢复入口不新建群 |
| 内容与对话换边 | 两个主面板的位置 | 阅读位置、选区、草稿、发送目标；不交换它们的数据 |
| 打开内容详情 | 内容区的对象与局部路径 | 当前聊天群和功能；返回恢复列表筛选、分页与滚动 |
| 划词 → 一起看 | 当前群草稿增加选中片段和出处；对话收起时展开 | 原文位置、原有文字与附件；不自动发送、不把整页替代选区 |
| 打开／关闭设置 | 内容区暂时进入／退出设置；保存原返回位置 | 原聊天和阅读状态；不重置到首页，不串入网页自身后退历史 |
| 查看全部上下文 | 聊天历史的显示范围 | 当前发送场景和 Being；不表示改变 Being 的记忆范围 |
| 收到通知或后台结果 | 对应来源的未读／状态 | 用户当前页面和焦点；点击后才定位来源 |

**随场景恢复阅读现场**沿用用户先前选择：A 群看到某封信，切 B 恢复 B 的阅读位置，再回 A 回到那封信。保存的是该聊天的界面位置，不把那封信变成 A 群拥有的数据，也不把别处的私信内容自动注入 Being。

对话的默认位置为右侧、默认展开；本轮建议将主动收起和左右位置作为显示偏好保持，避免每次换栏目强行展开。每场景分别记录阅读栏目、对象、筛选、滚动和内容是否展开。没有上次阅读位置的新场景进入纯对话。

边界：纯对话时不提供会让主区域变空的“收起对话”；点击“对话”或选中没有阅读现场的场景，明确恢复聊天。内容存在时才允许把对话收成右下角入口。避免“内容关闭了、聊天也藏起来了”的死路。

“全部上下文”的事实校正：`MULTI-SCENE-CALL-FLOW.md` 的旧稿写了只读，但当前 `chat/page.tsx` 与 `scene-runtime.js` 仍保留发送、附件与停止入口。现行事实是**显示范围变化，发送仍归当前场景**。本轮不擅自删除这些能力；后续 UI 在此范围明确显示当前发送目标。

沿用旧清单编号便于核对。编号是功能覆盖索引，不表示旧稿的布局建议继续有效，也不代表逐项通过真实客户端验收。

| 原清单 | 功能 | 新归属与往返规则 |
| --- | --- | --- |
| A01–A04 | 启动、首次连接、恢复、主空间 | 恢复上次聊天与内容；首次连接是设置中同一份连接表单。已有连接不用经过额外“进门页” |
| B01–B04 | Being 菜单、帮助、更新、反馈 | Being 名称管资料／自主醒来；设置管配置；帮助／更新进底部更多。错误留在所属操作，重要错误不只闪 Toast |

| D01–D08 | 聊天流、输入、附件、队列、过程、停止、后台任务、索引与搜索 | 都属于当前聊天。索引／查找在对话内定位，搜索不顶掉内容；运行与结果归原场景，后台消息不抢焦点 |

| E01–E02 | 篝火、筛选搜索、引用回复、公告 | 篝火内容页；公告只在该来源中展开，不覆盖对话 |

| E06、F01–F03 | 私信、收发范围、回复、代发身份、委托发送、结果 | 私信内容页内阅读与回复；原信保持可对照。主聊天输入与私信发送框分开，接收方、发送身份与可见范围在提交处明确 |
| G01–G05 | 花园搜索、种子详情、步骤、经验、派生关系、内化记录 | 花园内容页。相关种子与经验有来源后退；统计、关系和内化名单按需展开，非全局导航 |
| H01–H03 | 书架、故事分段、卷轴目录与详情 | 各自内容页；公开／我的、类型、分页是页内筛选；目录 → 详情 → 片段，返回保留原位置 |
| I01–I04 | Grove Kit／App、元信息、经验墙、反馈与讨论 | 工具库内容页；对象详情及关联内容有来源返回。App 仍只去发布者来源，不伪装成可安装 Kit |
| I05–I06 | 安装审阅、配置、执行、结果 | 工具详情内部的连续步骤；安装进度归该工具，可离开。完成保留当前页，提供查看本机入口；本机详情能返回原工具来源 |
| I07–I09 | 本机 Kit、导入、配置、删除 | 工具库的“本机”范围；同一工具详情，不另开全局设置副本。系统选目录继续使用原生选择器；删除仍说明具体范围 |

| M01–M03 | 设置、外观阅读、通知、客户端启动 | 唯一设置页面的分类；记住所在分类。窗口菜单和快捷键打开同一个页面 |

| M07–M08 | Portal 运行、启动停止重启、日志、诊断导出 | “设置 → 本机 Portal”与“诊断”；工具缺配置可以定向跳入再回该工具。运行状态快捷入口指向同一详情 |
| N01–N02 | Being 资料、隐私 | Being 名称可查看资料；完整说明在对应内容页／帮助中，不套第二层全屏弹窗 |
| N03–N07 | 系统菜单、托盘、窗口生命周期、通知、更新恢复、局部菜单 | 保留原生生命周期。关窗、收对话、退出、停止服务分别执行；通知定位真实可提供的来源；系统对话框仅用于选择器、必要确认等短操作 |

## 5. 六条完整流程

### 私信里商量怎么回复

私信 → 打开原信 → 划出想讨论的一段 → 一起看 → 右侧当前群出现引用 → 继续商量 → 将选定回复采用到私信回复框 → 在私信处发送。

原文一直在内容区；两份草稿分别保存：聊天草稿属于群，私信回复草稿属于收件对象／回复对象。采用文本不自动提交；已有回复草稿时不能静默覆盖。现有“委托拟写并发送”是另一条明确的对外执行动作，保留明确名称，不与“一起看”或普通讨论共用入口。

### 切群，再回原信

A 群正在看信和讨论 → 从左侧列表选 B → 保存 A 的输入与阅读状态，恢复 B → 再选 A → 回到原信、滚动和 A 群草稿。A 的回复或任务即使在后台完成，也只更新 A 的状态。

### 从篝火看卷轴，再返回

篝火某条发言 → 内容链接 → 卷轴详情 → 划词讨论 → 返回来源发言。功能选中态反映实际内容目的地，跨栏目来源路径仍可回退；返回不切聊天群。页面内部的“返回目录”和跨来源的“返回原文”名称准确，不能用同一按钮做不可预测的跳转。

### 从工具库安装，再回到之前的位置

工具库筛选列表 → Kit 详情 → 安装审阅／必要配置 → 执行 → 留在详情看结果；可选“查看本机” → 对应已安装 Kit → 返回安装来源。取消审阅回原详情；安装中切去别处不取消安装，完成不抢回页面。已安装、配置齐全、服务授权、工具可用分别依据真实状态显示。

### 配置完后回到正在做的事

私信／工具／聊天 → 设置的准确分类 → 子项 → 保存或取消 → 返回设置分类或原调用对象。只用一套路由与表单；设置内跳转不再层层弹窗。连接切换等真实身份变化另做状态隔离，不能把旧私有内容当新身份的恢复现场。

### 收起对话，再划词

内容和聊天并排 → 收起对话 → 长文使用释放的空间 → 划词点“一起看” → 恢复同一个聊天群并附上引用。普通选择、复制不展开聊天；新消息到达也不强制展开。手动点右下角只恢复对话，不新增引用或清空正文。

## 6. 设置如何消除重复

一个左下角入口，内部按作用对象组织：

| 分类 | 内容 |
| --- | --- |
| Being 与连接 | 当前 Being、连接链接、Being 模型配置；资料可从名称快捷查看 |
| 本机 Portal | 工作目录、能力开关、subagent 模型、后台运行、进程／Relay 状态与日志 |
| 小镇连接 | 配对身份、自动／手动配对、已有凭据、断开 |
| 外观与通用 | 主题、阅读字号、通知、客户端登录启动 |
| 关于与诊断 | 版本、更新、诊断导出、隐私与帮助 |

名字菜单里的 SBS 快捷开关、工具缺配置时的跳转、系统菜单“设置”都指向同一状态和目标；多个入口不等于多份设置表单。工具安装配置留在对应工具步骤里，不能误叫全局连接设置。

普通阅读、详情、回复、安装、长配置表单退出模态结构。短菜单、成员小预览、文件选择器和必要的破坏性确认仍可使用局部浮层或原生对话框，不为“去模态”再造新复杂流程。

## 7. Codex 参考具体取什么

用户截图清楚呈现了两级导航：最外图标栏，内侧是新聊天与列表，当前聊天在列表中选中。这里采用其**功能切换与聊天选择分层**的组织，不复制项目／worktree 层级，也不把每个小镇栏目变成聊天群。

[官方 Commands 文档](https://learn.chatgpt.com/docs/reference/commands) 分别列出切换侧栏、前后导航、切换聊天、切换浏览器面板等操作；说明这些动作需要各自明确的对象。本设计也把功能、群、面板可见性分开。

本轮尝试读取本机 Codex 被工具安全限制拒绝，未绕过限制。因此截图中的视觉层级与官方列出的操作是本轮依据；未声称实测该安装版本所有切换、恢复及动效。浏览器标签不再作为应用级导航参考；它是否支持分屏不影响这里的选择，选择图标栏的原因是固定目的地和聊天选择更容易分层。

## 8. 从旧 spec 保留什么、纠正什么

保留：中性色、系统字体、文字主导、安静的层级、真实状态、草稿与阅读连续性、可见且可键盘到达的入口。独立主区域的圆角边界、分栏边界与间距在此架构之后统一处理，不在每个条目外再套卡片。

纠正：不再强制启动先过“进门页”；不把场景解释成材料收纳箱；不增加“物件／搁置／保留”等未经本轮确认的新一级概念；不把整页“一起看”作为主流程；不以顶部长标签排组织固定小镇栏目；不把多窗口、自由停靠、Being 自动排版一并塞进本轮基础导航。

Being 的持续身份、记忆与自主活动继续成立。内容在屏幕上不等于 Being 已读取；客户端不靠向正文插入隐藏协议让它假装感知。将来让 Being 打开／安排视图时，复用同一组操作、保留人的编辑位置；界面动作与对外发送分别处理。完整环境感知和 Being 控制界面仍是待接协议能力。

## 9. 代码依据与下一轮边界

- [`desktop/main/chat/scene.ts`](../desktop/main/chat/scene.ts)：按 Being endpoint 保存场景目录；新建、绑定、选择、改名、移动及移除的实际范围。
- [`chat/services/scene-runtime.js`](../desktop/renderer/chat/services/scene-runtime.js)：切换场景保存原草稿，发送捕获当前场景；活动运行分场景管理。
- [`chat/page.tsx`](../desktop/renderer/chat/page.tsx)：现有聊天划词与“一起看这段”；全部上下文仍有输入入口。划词功能也存在于当前 HEAD，不是本轮 Demo 发明。
- [`town/components/feed.tsx`](../desktop/renderer/town/components/feed.tsx)：小镇目前还存在整条消息的“一起看”按钮。**不能声称所有内容面板已经支持划词**；本轮是确定统一的交互目标。
- [`town/components/composer.tsx`](../desktop/renderer/town/components/composer.tsx)、[`town/models/town.ts`](../desktop/renderer/town/models/town.ts)：私信／篝火／围炉发送身份、草稿、委托发送、详情与安装来源。
- [`app/components/settings.tsx`](../desktop/renderer/app/components/settings.tsx)、[`portal/page.tsx`](../desktop/renderer/portal/page.tsx)：当前设置总页、连接表单与 Portal 设置的拆分，后续需要归一。
- [`SHARED-WORKSPACE.md`](../desktop/SHARED-WORKSPACE.md)：人和 Being 可以各看各的；来源与选区需要保留；完整双向协议仍有草案部分。

下一轮只验证同一结构中的四条链：点功能但群不变；左侧切群并恢复阅读；划词讨论后在原处回复；收起后原样回来。使用真实组件做可操作预览，随后在 Electron 核对原生浏览器、焦点、输入法及真实状态。尚未进行本轮 UI 实现或客户端验收。

这些是状态保留的目标，不代表现有所有草稿已能跨重启恢复；小镇部分草稿目前仍是内存缓存，网页内部表单也不能仅靠恢复 URL 保证恢复。后续接线需逐项验证，界面不得提前声称已经保存。
