## 1. 本轮修正

上一轮把“左侧场景、中间固定对话、右侧内容”过早收敛成唯一组织。它可以是一种好用的默认排列，却不足以承载专注阅读、比较资料、双屏工作，以及 Being 在别的软件里陪同做事。

**建议将场景与呈现分开：场景记录共同经历、正在做的事及其来源；标签、分屏、浮窗和独立窗口决定眼前怎样看。**同一个 Being 可以出现在这些呈现中。打开新标签、拖出窗口、放大内容都不自动新建 Being 或聊天场景。

用户已确认的“随场景恢复各自的阅读现场”继续成立。本轮扩大“现场”的范围：它可以包含几个对象、布局、讨论位置和窗口安排，不再默认只有一个右侧页面。多窗口的实际恢复能力还需要实现。

本稿取代 [上一轮复审](ux-audit-interaction-architecture-2026-09-27.md) 中固定区域作为唯一方案的推荐；其问题证据、73 项功能清单、设置独立返回、草稿保护和真实状态要求仍保留。

## 4. 展开六种能力，再选择默认方式

| 能力 | 最适合 | 需要解决的负担 |
|---|---|---|
| 临时预览 | 看一眼人、消息、Kit、引用来源 | 不能覆盖正在写的内容；Esc 回准确来源 |
| 标签页 | 几份材料轮流看，稍后回来 | 区分临时与保留；防止每次点链接新增永久标签 |
| 并排面板 | 一边看信一边讨论；两份原文对照 | 最小可用宽度、明确焦点、独立滚动；窄屏改为可切换展示 |
| 内容独立窗口 | 长文、第二屏、长期参照 | 归属哪个场景、关闭后去哪、屏幕移除后的恢复 |
| 浮动对话 | 在浏览器、编辑器等外部应用临时与 Being 商量 | 当前发送场景必须可见；不随鼠标焦点暗中换场景；可以停靠回主界面 |
| Being 安排内容 | “帮我比较这两份”“把回复现场准备好” | 尊重编辑与明确保留的位置；可恢复；不把布局授权当发送或改身份授权 |

这六种不是六套彼此独立的产品模式。同一封信可以从预览变成标签，再并排或移到另一屏；对象、草稿和行动保持连续。

### 三种主组织候选

| 候选 | 日常体验 | 强项 | 主要代价 |
|---|---|---|---|
| **A · 按场景保留现场，内容可组合，推荐** | 打开上次那件事；对话和相关内容按需要摆放；Being 也能整理 | 对应已确认的场景恢复；适合阅读、社交与做事混合 | 要区分聊天场景与资源来源，并建设可靠的视图状态 |
| B · 内容浏览器 + 常伴浮窗 | 小镇、资料、工具占主体；随时唤出同一个 Being；重要交流再归入场景 | 跨应用更直接；不要求先进入聊天页才能做事 | 容易不清楚刚才的讨论属于哪里；浮窗会遮挡；需显式场景绑定 |
| C · 完整可停靠工作台 | 像 IDE 一样任意分组、拖出、排列；自己保存布局 | 多屏和密集研究最强 | 布局管理可能比原任务更复杂；普通日常使用容易变吵 |

建议以 A 为默认，吸收 B 的快捷陪伴和 C 的按需组合。B / C 都可以成为用户选择的呈现，不必先被否定，也不必作为所有人第一次打开的复杂界面。

## 5. 推荐的操作规则

### 场景、内容、窗口各管一件事

- **切场景**：恢复这件事的讨论、内容、阅读位置和布局。场景切换入口保持稳定；可以在左上切换器，也可以展开场景目录，不要求目录永久占宽。
- **打开内容**：打开某份材料或一个场所，归入当前现场。小镇可以铺满主要区域，也可以与讨论并排，不被永远限制在窄右栏。
- **换呈现**：标签切换、并排、放大、浮动、移到新窗口，只改变视图。对话内容和当前发送目标不会因此自动变更。
- **设置**：仍是独立配置层。多个窗口中的入口到同一个设置状态；设置不成为普通内容标签，也不混入阅读后退。

### 少量稳定动作，组合出更多可能

1. **查看**：在临时阅读位置打开。连续查看下一条不堆积永久标签。
2. **保留**：明确留下一个对象；开始编辑后也保护它，不被后续点击替换。这里是新的内容保留能力，不冒称现有“固定侧栏”已经实现。
3. **并排查看**：把两份内容同时摆开。可以是“对话 + 原文”，也可以是“原文 + 原文”。拖到边缘是快捷方式，菜单 / 键盘也能完成。
4. **放大 / 恢复排列**：暂时聚焦一份内容，再回原组合。没有丢掉其他内容。
5. **移到新窗口 / 移回主窗口**：移动同一个视图。高级“另开同一内容的视图”可以后加，但必须共享同一份草稿，不复制发送事务。
6. **恢复刚才布局**：撤回一组窗口或面板安排。它只恢复展示，不撤销已经发送的信或安装的工具。

**标签分层：**场景是正在做的不同事情，内容标签是同一件事里的材料。先采用场景切换器 + 内容标签，避免两排外观相同的 tabs。只有一个内容时，不显示多余标签框。左侧是否常驻由空间与使用方式决定。

**关闭分层：**关闭预览回来源；关闭标签移除这个视图；关闭副窗保存现场并可回主窗继续；停止生成和退出客户端是独立动作。不能用同一个 X 暗中承担不同级别的数据删除。

**先保护再安排：**正在输入、有未提交编辑、明确“保留”的面板不会被自动替换。新材料使用其他可用位置，或作为未激活标签加入；新增内容不必同时挤进屏幕。

### 同一现场的四种呈现示意

```text
一起商量                  专心阅读
┌─────────┬─────────┐     ┌───────────────────┐
│ 与 Being │ Alice 原信│     │ Alice 原信 / 回复正文 │
│ 的讨论   │ + 回复草稿│     │           [继续讨论] │
└─────────┴─────────┘     └───────────────────┘

比较资料                  跨应用 / 第二屏
┌─────────┬─────────┐     主窗口：原信与资料
│ 资料 A   │ 资料 B   │     另一窗口：同一场景的讨论
└─────────┴─────────┘     场景名始终可辨；可以移回
讨论可以收起、停靠或浮动
```

这是结构草图，不是组件与视觉定稿。圆角、标题栏、拖拽提示和焦点样式必须围绕同一对象在不同呈现间的连续变化设计，而不是每种模式换一套皮肤。

## 6. Being 能决定什么

本轮已询问用户偏好的布局主动程度：直接安排并可恢复、先建议后应用、开启跟随后安排。**尚未得到答案时，以下“当前场景内直接安排”只是推荐，不标记为用户已批准。**

建议把能力分为三层，而非一个“AI 控制界面”总开关：

| 范围 | 推荐行为 | 例子 |
|---|---|---|
| Being 自己查看和整理 | 在任务授权范围内进行，记录来源；不切人的当前页 | 后台查三份卷轴，带回相关两份 |
| 当前场景的展示 | 当人在让它处理这件事时，可以打开相关内容、并排、放大；保护编辑、提供恢复 | “帮我比较这两份”后安排左右对照 |
| 其他场景、其他窗口与持续跟随 | 人明确要求或开启跟随后再改变；切场景 / 开始手动编辑即暂停持续跟随 | “把这份放到另一屏”“接下来跟着你看” |

不是每次开面板都弹确认。没有必要的动作不打断；被人固定的内容保持稳定；用户一次恢复后不立刻被 Being 再次改回。连续自动安排可以收起成同一条“Being 整理了这些内容 · 恢复布局”记录，不连发 Toast。

Being 也可以提出“这次适合用两份原文并排”的建议。遇到窄窗口或正在编辑时，优先准备内容并等待展示机会，而非擅自缩小正文、收起草稿或另开一串系统窗口。

### 生成式界面的范围

第一阶段让 Being 选择和组合已实现的私信、文档、网页、对话、工具结果视图，沿用相同的打开、关闭、来源和草稿规则。之后可以增加任务需要的新内容表示，如对照表、时间线，但它们仍是可引用、可编辑、可恢复的对象。

Being 决定任务呈现，客户端保证稳定操作规则。布局动作、发信、删除、安装、凭据授权有不同影响，不能互相替代授权。普通自然语言意图不被强制改造成表单或协议文本。

## 7. 用真实事情推演

### 看私信并回复

从小镇打开 Alice 私信，可先整页阅读。点“一起看”或唤出当前场景的讨论后，形成原文 + 对话并排。Being 拟出建议，用户采用到原信的回复草稿；草稿一旦编辑就保持位置。若要查另一封信，先预览或新标签，不覆盖草稿。窄屏用对话 / 原文切换，同一个讨论和正文继续保留。

### 比较两份卷轴

不需要强行让中间对话继续占最大面积。选两份 → 并排；讨论停靠为小面板或临时浮出。Being 指向具体片段，有稳定来源。比较结束恢复原排列，两份卷轴可留在内容标签中。

### 工具安装期间继续聊

Kit 详情中发起安装；审阅结束后进度归属于该工具与发起场景。可以切到讨论、另一标签或另一窗口。结果不会把当前阅读替换成“安装成功”页；在原 Kit 中继续配置或验证。离开来源没有取消安装，重新打开也不启动第二次。

### 在其他软件里工作

用户主动唤出 Being 小窗，窗上明确“与美阳阳 · 工作讨论”。共享选中的内容或明确的屏幕范围后讨论；外部应用切焦点不会暗中把发送目标换到另一个场景。需要长期共同查看时，移入完整场景，或固定小窗；默认不永远置顶。

### 多窗口、切场景再回来

窗口一是工作讨论，窗口二是日常聊天，各自输入目标独立。切窗口一的场景不改变窗口二。将工作中的原信移到副窗只改变视图归属，不创建另一份信或草稿。

同一场景同时出现在两个窗口时，源数据和编辑草稿共享，焦点、滚动、布局按窗口独立。先支持一个活动编辑位置，另一处可明确接管；未解决同步冲突前不宣称可以在两处同时编辑。窗口关闭后重开，副屏不存在则把窗口收回当前可见屏幕。

### Being 与人各看各的

人继续写信，Being 在后台查参考。不把它每一步浏览都镜像到用户屏幕。结果出现后用户可以展开，或者明确开启跟随。跟随过程中人开始操作就优先保持人的位置；后台执行继续，不等于停止任务。

## 8. 所有功能如何进入同一套规则

上一轮 73 项功能的存在与边界不变，改变的是呈现方式。详见 [全功能图谱](ux-audit-desktop-full-2026-09-27.md)。

| 类别 | 组合规则 |
|---|---|
| 对话、场景信息、历史查找 | 对话是一种可停靠的视图；信息 / 查找是其局部操作；发送目标固定到聊天场景 |
| 小镇概览、篝火、围炉、私信、通讯录、公告 | 可以独立浏览、预览或加入讨论现场；阅读源身份和发送身份始终准确 |
| 花园、书架、卷轴及关系详情 | 内容视图可标签、并排和移出；关系链接保留访问来源；大纲 / 成员等局部详情不默认变永久标签 |
| 工具库、本机工具、安装与配置 | 目录与详情是内容；安装是独立事务；具体工具配置是对象操作；全局能力开关仍在设置 |
| 网页 | 一种内容视图；地址、网页历史、返回来源分别明确；登录态与场景恢复不能混为一谈 |
| Being 资料、SBS、模型、Portal、小镇配对、诊断 | Being 资料可从其姓名查看；设置保持同一编辑状态和调用来源；读配置 / 改配置与讨论引用区分 |
| 通知、后台结果、更新、系统窗口 | 结果定位原对象和发起场景；通知不移动其他窗口；关闭视图不等于结束事务或关闭 Being |

因此，小镇不会退化成打开菜单中的一个图标；它有自己的完整内容视图，也可以与讨论组合。统一的是对象与动作，不是强迫所有内容套一套窄侧栏。

## 9. 当前实现的真实边界

- `desktop/main/main.ts:73` 是一个主窗口变量；第 279–280 行 IPC 只信任该窗口的主 frame。多窗口需要注册每个受信窗口，不能简单去掉校验。
- `desktop/main/chat/scene.ts:35` 的会话组只有一个 active；主进程快照按它返回当前场景。需要把每个窗口的选中场景与共享场景目录分开。
- `desktop/main/chat/proxy.ts:45` 已能按发送请求的 `X-Portal-Scene-Id` 解析有效场景，不能忽略这个已有保护并声称所有发送只取全局当前场景。未来仍需核验发送窗口、视图与连接归属。
- 现有按 scene_id 分流的 runtime、草稿和 SSE 路由可以复用；它不自动保证不同 BrowserWindow 里的重复请求、停止、流订阅和编辑状态协调。
- `SceneStore.current` 是一个当前内容观察。多面板 / 多窗口需要多个 view 与可见范围，消息发送时捕获的是当时明确引用或选择的对象，不能读取后来变化的全局 current。
- 原生浏览器目前随主窗口建立一个 `ClientBrowser`。多个网页视图与跨窗移动要明确实例、会话分区、冻结、关闭和恢复成本。恢复 URL 不等于恢复网页内部表单。
- 完整 `scene.observe / scene.act` 与 Heart 的 UI 能力协商仍是本地文档中的后续协议；本轮没有把布局自主安排冒充已接通功能。

工程上要先建设视图身份、共享内容、编辑归属和动作记录，再逐步增加呈现方式。无需为此先更换 Electron 技术栈。本轮使用 native-feel 的 T3 平台窗口 / 焦点约定与 T7 熟悉操作连续性，未采纳其整套框架迁移方案或未经本项目测量的性能数值。

## 10. 下一步验证顺序

先比较三个完整的小流程，而不是继续画一张静态首页：

1. **信件现场**：整页阅读 → 并排讨论 → 采用草稿 → 临时离开 → 原处恢复。
2. **资料比较**：两份原文并排 → 对话停靠 / 浮动 → 移到副窗 → 移回；来源与编辑内容连续。
3. **Being 安排**：表达目标 → Being 选出相关材料并安排 → 用户编辑保护 → 恢复布局；后台任务不被撤销。

检验人能否直接回答：现在和谁、在哪件事里讨论；这里是哪份内容；关闭会发生什么；Being 刚改了什么；怎样回到刚才。先用可点原型比较，再以真实客户端验证键盘、输入法、跨窗焦点、系统窗口恢复与流状态。

**当前研究结论：默认简单，场景连续，视图可组合，Being 可以参与安排。**自主程度待用户回答；首版是否包含系统级浮窗与多窗口需结合原型结果取舍。没有将这份研究标为已经批准的实现规格。
